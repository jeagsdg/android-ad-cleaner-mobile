# 从源码构建

需要 JDK 17 或 21、Android SDK 35。在仓库根目录运行以下命令。Windows 将 `./gradlew` 换成 `.\gradlew.bat`，也可以使用 `tools/build.ps1`。

```sh
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
./gradlew -PofflineOnly=true :app:assembleDebug
python tools/verify_sources.py
```

## 发布构建

在 Windows 运行 `tools/build.ps1 -Release` 生成完整版，追加 `-OfflineOnly` 生成纯离线版。发布签名从本机 `.local/signing.properties` 读取 `storeFile`、`storePassword`、`keyAlias` 和 `keyPassword`。自行构建时使用自己的密钥，配置和密钥保留在本机。

发布 APK 时递增版本号，同步 `dist` 两种安装包与 `SHA256SUMS.txt`、根目录的 `update.json` 和 `.update.json`、`0-update` 的完整版镜像。公开归档中的更新文件须符合客户端的流式读取限制。 [归档读取实现](../app/src/network/java/app/clearscreen/GithubReleaseFiles.java)

### 可重复的本地候选

在 PowerShell 7 运行下列命令。候选目录选用项目外全新的英文路径。本机提供 Android SDK、JDK 和发布签名，项目的 `.local` 只供本地构建读取。源文件在构建前冻结，输出包含两种正式签名 APK、同证书的 Android 仪器测试包和构建输入摘要。测试包用于设备回归，公共分发只包含前两种。

```powershell
./tools/build_signed_candidate.ps1 -CandidateDirectory C:/build/clearscreen-candidate
```

准备发布时，从上一版 GitHub 主分支 ZIP 及其提交 SHA 开始。先用 `python tools/stage_release.py --previous-archive <zip> --parent <sha>` 列出变化，逐项核对后保存为 UTF-8 文件，每行一个完整路径。需要公开的新验收记录可用 `--evidence artifacts/文件名` 显式列入，两次命令使用相同选项。然后在命令末尾追加 `--allowlist <文件> --binaries <候选目录> --output <新暂存目录>`。工具验证签名、版本、联网权限、规则增量和历史校验值，生成待提交文件与一项旧镜像移除记录。

若签名后只修正了 JVM 测试，可独立重跑受影响的测试，再传入 `--verified-tests <回归凭据.json>`。其中的 `files` 对象记录实测文件的项目相对路径及 SHA-256。验收清单会保留这份差异。变更生产代码、资源、构建设置、设备测试或夹具时需要重建相应候选。

在独立 Git 工作区将同一清单组成一次提交。用 `git archive --format=zip --prefix=android-ad-cleaner-mobile-main/ --output=candidate.zip HEAD` 生成预检 ZIP，再运行 `python tools/stage_release.py --previous-archive <旧zip> --parent <旧sha> --verify-archive candidate.zip --manifest <暂存目录>/manifest.json`。工具逐文件核对完整文件树与字节，并检查 Android 客户端的 128 项、前置内容 4 MiB 查找上限。发布后对公开主分支的 ZIP 重复这一步并回读两个安装包。Secrets、测试签名配置、诊断原文和设备工件保留在本机。

## 签名规则包

查看 `python tools/publish_rule_pack.py --help` 获取签名规则包参数。发布时递增规则包版本并验证 APK 兼容范围。新增或替换规则需有明确的广告场景、准确的 Activity 和应用自身的关闭控件，逐条启停状态保留在本机。 [规则来源](../NOTICE.md)

2.2.0 至 3.0.0（版本号 22–27）均接受 `0-update/rules-v22.json` 中为版本号 22 签名的 v5 规则包。版本号 27 恢复 v5 时核对原有行并保留 APK 内新增候选。版本号 19–21 继续使用 `0-update/rules.json` 中的 v3 规则包。

## 历史验收记录

早期验收文档、截图、测试摘要可在对应历史提交中查看。 [验收归档](https://github.com/jeagsdg/android-ad-cleaner-mobile/tree/8dbff795bc19104fdac5652e72a38f81aed535f2/artifacts)

3.0.0 可读取独立的签名增量。构包工具的 `--delta` 选项按 APK 两份内置目录的原始 UTF-8 字节校验基底，用有序整数引用未变化的规则，新增和替换行使用受限规则格式。增量输出使用 `--output 0-update/rules-delta-v2.json`，旧客户端继续读取原来的全量文件。两个渠道的版号都应随对应目录递增。完整版检查到新包后可预览增删和顺序变化，确认后才原子切换，重启前未确认的预览可重新检查。

对外新增或替换的规则需有稳定的规则 ID。构包时给出 `--reviews review.json`；其中每个 ID 对应 `positive`、`negative` 两个路径，路径相对于 review.json。样本须是本地净屏 JSON，普通页面样本与广告页面属于同一应用。构包工具在签名前通过 Android 单元测试入口复核新目录的兼容范围、字段、重复目标和两份样本的匹配性。缺样本、广告页命中数不为 1 或普通页命中数不为 0 都会终止。此步骤不会把样本写进规则包。
